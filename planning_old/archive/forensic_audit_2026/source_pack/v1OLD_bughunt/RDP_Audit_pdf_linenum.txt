PDF p01 l01: RuneDecrypterPrime Codebase Forensic Audit
PDF p01 l02: This  audit  identifies  subtle  bugs,  broken  assumptions,  and  ambiguous  contracts  in  the
PDF p01 l03: RuneDecrypterPrime (RDP) codebase that could derail complex cryptanalysis solves. The focus is on scoring
PDF p01 l04: precision, solver logic, key operations (KeyOps) fidelity, and representation integrity (e.g. WLI semantics).
PDF p01 l05: Each  issue  is  described  with  evidence  from  the  code,  followed  by  severity  and  recommendations.  A
PDF p01 l06: summary  of  integration  tests  and  open  design  questions  is  included  at  the  end,  along  with  clear
PDF p01 l07: recommendations  for code and contract improvements.
PDF p01 l08: Scoring Pipeline and Precision Issues
PDF p01 l09: Overview:  The scoring pipeline exhibits several weaknesses that can silently degrade solver performance
PDF p01 l10: on  hard  problems.  These  include  mis-specified  objective  direction,  enforced  low-precision  floats,  and
PDF p01 l11: improper handling of optional WLI (Word Location Index) inputs. These issues risk non-deterministic or
PDF p01 l12: incorrect score comparisons, causing plateaued solves or misguided search.
PDF p01 l13: rune_scorer.py  – Objective Direction Misalignment (NEGLOGP vs Maximize)
PDF p01 l14: RDP’s scoring configuration provides an  ObjectiveFamily  (e.g.  NEGLOGP  for negative log-likelihood)
PDF p01 l15: and a boolean  maximize  flag. In practice,  solvers assume “higher score = better” regardless of the
PDF p01 l16: flag,  creating  an  implicit  contract  that  all  objectives  must  be  maximized .  However ,  the  NEGLOGP
PDF p01 l17: objective returns the negative  average log-probability  – meaning a lower (more negative) raw value is
PDF p01 l18: better , but the solver will mistakenly treat higher (less negative) values as better . This silent sign error  can
PDF p01 l19: cause solvers to optimize in the wrong direction while telemetry appears normal. The solver’s accept/reject
PDF p01 l20: checks (e.g. using > for improvements) are all geared for maximize-mode , so a minimizing objective
PDF p01 l21: violates assumptions.
PDF p01 l22: Evidence:  In code, the ScoringConfig.maximize  flag is defined but never enforced; solvers always sort
PDF p01 l23: and compare scores in descending order . Meanwhile, the NEGLOGP implementation explicitly negates
PDF p01 l24: the log-probability before returning . This mismatch means if NEGLOGP is used, the solver believes it’s
PDF p01 l25: maximizing a positive score when it should be minimizing a cost.
PDF p01 l26: Impact:  This  issue  is  solver-blocking  if  a  minimizing  objective  (like  NEGLOGP)  is  ever  used  without
PDF p01 l27: modification .  The  search  may  diverge  or  converge  to  incorrect  solutions,  because  it  is  effectively
PDF p01 l28: rewarding  worse solutions.
PDF p01 l29: Recommendation:  Either disallow use of NEGLOGP (or any minimizing objective) with the current solvers,
PDF p01 l30: or update solver logic to honor the  maximize  flag. At minimum, add a  guard  to raise an error if a
PDF p01 l31: minimize-type  objective  is  combined  with  an  assume-maximize  solver .  An  integration  test  should
PDF p01 l32: construct two scores (one clearly better in a minimizing sense) and verify the solver correctly prefers the
PDF p01 l33: true optimum or fails loudly. (See Proposed Tests  below.)1

PDF p02 l01: rune_scorer.py  & unified_rune_scorer.py  – Floating-Point Precision
PDF p02 l02: Enforcement (Float32 vs Float64)
PDF p02 l03: Throughout the scoring pipeline, scores are  downcast to 32-bit floats , undermining precision on tough
PDF p02 l04: differentiations. Two critical points stand out:
PDF p02 l05: ECDF interpolation:  When scoring uses ECDF (empirical CDF) normalization, intermediate
PDF p02 l06: calculations cast inputs to np.float32  and produce float32 outputs . Even if a higher precision
PDF p02 l07: (float64 ) is requested, the interpolation forces 32-bit results.
PDF p02 l08: Batch scoring adapter:  The UnifiedRuneScorer  wrapper unconditionally casts batch scores to
PDF p02 l09: float32 , regardless of the backend’s dtype or user preference. Additionally, the NumPy batch
PDF p02 l10: scorer pre-allocates an output array in float32 . 
PDF p02 l11: Evidence:  The  code  explicitly  uses  np.asarray(...,  dtype=np.float32)  during  ECDF  score
PDF p02 l12: computation  and  returns  results  as  float32.  In  the  unified  scorer ,  we  see  return  
PDF p02 l13: np.asarray(self._backend.batch_score(...), dtype=np.float32) ,  ensuring  that  even  a
PDF p02 l14: float64 backend result is truncated. This means a user setting  dtype="float64"  in scoring config will
PDF p02 l15: not actually get 64-bit precision where it matters .
PDF p02 l16: Impact:  On easy puzzles, float32 may be sufficient. But for  hard multi-phase ciphers with tiny score
PDF p02 l17: differences , this can be solver-blocking : near-tie candidates can become indistinguishable due to precision
PDF p02 l18: loss, causing plateaus or incorrect beam ordering . Non-deterministic tie-breaking can also occur if
PDF p02 l19: scores quantize to identical float32 values when they differed in float64.
PDF p02 l20: Recommendation:  Honor the dtype setting end-to-end, or at least document that all internal scores are
PDF p02 l21: float32. Ideally, the unified scorer should preserve backend precision or perform comparisons in higher
PDF p02 l22: precision before casting for storage. A dedicated test should feed two nearly-equal scoring candidates (with
PDF p02 l23: a very small known difference) and assert that a float64 pipeline can discern the better candidate while
PDF p02 l24: float32 might not .

PDF p03 l14: language_model_prime.py  – Language Model Smoothing Cache Contamination
PDF p03 l15: RDP’s language model scorer caches loaded n-gram tables by file path. A hidden issue is that  the cache
PDF p03 l16: does not account for smoothing or OOV (out-of-vocabulary) settings , and the native code modifies the
PDF p03 l17: cached data in place  when applying smoothing. This means if two scorers load the same model file with
PDF p03 l18: different smoothing parameters, the first scorer’s settings can bleed into the second’s results  without any
PDF p03 l19: indication.
PDF p03 l20: Evidence:  The _load_bin  function uses a module-level cache _load_bin_cache  keyed only by the file
PDF p03 l21: path .  If  a  path  is  in  the  cache,  it  returns  previously  loaded  arrays  by  reference .  The  native
PDF p03 l22: FastTransitionModel  in fastlm.cpp  takes smoothing parameters (like Laplace alpha or Good-Turing
PDF p03 l23: flags) and overwrites the logp probability array in place with smoothed values . Thus, a second
PDF p03 l24: scorer that retrieves the same cached  logp array will get it  already smoothed  with potentially different
PDF p03 l25: parameters than it asked for . There is no versioning by smoothing/OOV policy.
PDF p03 l26: Impact:  This  cross-contamination  is  solver-degrading  and  audit-hostile .  For  example,  a  scorer
PDF p03 l27: configured with no smoothing might unexpectedly receive Good-Turing smoothed probabilities if another
PDF p03 l28: scorer earlier in the process used that model with smoothing. This can shift score values mid-run or
PDF p03 l29: between runs, confusing tuning and making results irreproducible across different scoring configurations.
PDF p03 l30: Recommendation:  Isolate language model assets per config. The cache key should include smoothing
PDF p03 l31: parameters (e.g.  (path, smooth_mode, oov_mode, alpha)  as suggested) , or the cached arrays
PDF p03 l32: should be immutable originals that each scorer copies and smooths on its own. A test for this could
PDF p03 l33: instantiate two scorers (one with smoothing off, one on) on the same model and verify that the first scorer’s
PDF p03 l34: results remain consistent before and after using the second scorer (no drift in scores) .

PDF p04 l04: pipeline.py  & solver_engine.py  – Inconsistent Determinism Defaults
PDF p04 l05: RDP’s main pipeline enforces a default RNG seed of 0 (for reproducibility) when none is provided, whereas
PDF p04 l06: the legacy SolverEngine  usage will use a fresh entropy-based RNG if no seed is injected. In other words,
PDF p04 l07: the same solve request can be deterministic or not depending on which API entry point is used .
PDF p04 l08: Evidence:  In  RunAPI.run() ,  the  code  normalizes  the  seed:  if  no  seed  is  given,  it  explicitly  sets
PDF p04 l09: effective_seed = 0 . This flows into the engine, which then uses np.random.default_rng(0)  –
PDF p04 l10: deterministic sequence each run . Conversely, if one bypasses the high-level pipeline and uses the lower-
PDF p04 l11: level  core.solver_engine ,  that  code  calls  np.random.default_rng()  with  no  fixed  seed ,
PDF p04 l12: yielding different sequences each time. The audit confirms this discrepancy .
PDF p04 l13: Impact:  This is  solver-degrading  for debugging and reproducibility . A user might assume “same
PDF p04 l14: inputs, same outputs,” but if they inadvertently use a different code path (e.g. a legacy interface or custom
PDF p04 l15: loop),  results  can  appear  flaky.  Hard  cryptanalytic  solves  may  fail  intermittently  due  to  uncontrolled
PDF p04 l16: randomness, undermining trust in the tool.
PDF p04 l17: Recommendation:  Unify determinism policy: ideally, default to a fixed seed (0 or a documented constant)
PDF p04 l18: in all entry points unless the user specifies otherwise. At minimum, warn when a non-deterministic path is
PDF p04 l19: used. A test should run the same solve twice via the legacy path with no seed and expect identical results or
PDF p04 l20: a clear warning .
PDF p04 l21: solver_base.py  – Silent Seed Key Replacement on Normalization Failure
PDF p04 l22: The solver initialization accepts user-provided initial key guesses (“seeds”). If a seed is invalid (e.g., wrong
PDF p04 l23: length or out-of-domain), the code  silently replaces it with a random key  without notifying the user
PDF p04 l24: unless even the random replacement fails. This behavior hides potentially critical input errors and changes
PDF p04 l25: the solver’s starting conditions unexpectedly.
PDF p04 l26: Evidence:  In  SolverBase.__init__ ,  the  provided  initial_keys  are  normalized  via
PDF p04 l27: self.keyops.normalize() . If normalization fails for a seed row (throws exception or returns None), the
PDF p04 l28: code catches it, logs a debug message, and generates a new random key via self.keyops.random(...)
PDF p04 l29: to use instead . Only if that also fails does it increment a “dropped seed” counter . Furthermore,
PDF p04 l30: when using composite ciphers (e.g., with interruptors), a valid seed must match the full composite key
PDF p04 l31: length (core key plus interruptor part); the code does not explicitly check this upfront, so a too-short seed
PDF p04 l32: will be treated as invalid and randomly expanded . Telemetry still counts these as “provided” seeds
PDF p04 l33: unless dropped, masking the event .
PDF p04 l34: Impact:  This is solver-degrading : a user might supply a specific starting key (perhaps from a prior run or an
PDF p04 l35: intuition),  but  the  solver  could  ignore  it  and  start  elsewhere  without  clear  indication.  Particularly  for
PDF p04 l36: composite  ciphers,  a  user  might  not  realize  they  needed  to  provide  a  longer  tuple  key.  Debugging
PDF p04 l37: performance or behavior issues becomes hard when the initial conditions are not what the user intended.25

PDF p06 l01: keyops/composite.py  – Composite Key Length and Variable-Interruptor Handling
PDF p06 l02: Composite ciphers (those that combine a primary key with interruptor positions) present tricky invariants
PDF p06 l03: that RDP currently does not enforce, leading to potential runtime crashes or solver dead-ends:
PDF p06 l04: Seed length vs composite length:  For composite ciphers, the full key is typically a concatenation of
PDF p06 l05: core  cipher  key  and  interruptor  indicators.  The  expected  length  is  core_K + interrupt_K .
PDF p06 l06: However , as noted above, if seeds are provided at the core length only, the system will accept them
PDF p06 l07: and  pad  randomly  rather  than  erroring .  This  is  partly  a  KeyOps  contract  issue:
PDF p06 l08: CompositeKeyOps.normalize()  checks that provided keys match the full length and raises a
PDF p06 l09: ValueError if not , but this may be caught and treated as “need random replacement” by the
PDF p06 l10: solver instead of stopping.
PDF p06 l11: Initial  permutation  vs  interruptor  removal:  If  an  initial  text  permutation  is  configured  and
PDF p06 l12: interruptors are in use, there’s a conflict. The API currently requires the permutation length to equal
PDF p06 l13: the full ciphertext length on input , but at runtime the cipher first removes interruptors (dropping
PDF p06 l14: characters) then applies the permutation, which must match the reduced  length . A permutation
PDF p06 l15: provided for the full length will pass initial validation (because it matches ciphertext length) but then
PDF p06 l16: cause a length mismatch error when applied after removal . Conversely, if the user tries to
PDF p06 l17: provide a permutation of the core length (to match after removal), the initial validation will reject it
PDF p06 l18: as wrong length . In short, there is  no way to supply a valid permutation when using
PDF p06 l19: interruptors , due to a structural contract bug.
PDF p06 l20: Variable interruptor count:  Some composite KeyOps allow the number of interruptors to vary per
PDF p06 l21: key (e.g., between min_count  and max_count ). This means different candidate keys will produce
PDF p06 l22: different core text lengths. A single fixed permutation cannot consistently apply to all, since the core
PDF p06 l23: length isn’t constant . RDP does not currently detect or prevent this scenario, so a solve that
PDF p06 l24: mutates  interruptor  count  while  holding  an  initial  permutation  could  crash  mid-search  with  a
PDF p06 l25: “text_perm must match text length” error when a key’s interruptor count deviates .
PDF p06 l26: Evidence:  The composite KeyOps code explicitly randomizes interruptor count within a range , and uses a
PDF p06 l27: special sentinel value to mark interruptor positions . The permutation application code throws an error if
PDF p06 l28: lengths  don’t  match .  The  pipeline  docs  and  code  clearly  expect  permutations  to  be  defined  after
PDF p06 l29: interruptor removal (core space) , but the implementation doesn’t allow specifying it that way. Also,
PDF p06 l30: ProblemSpec  validation demands permutation length == original text length . For interruptor pool
PDF p06 l31: values, the config only checks that indices are non-negative and unique , and actual range validation
PDF p06 l32: (idx < length ) happens only at decrypt time , i.e. after the solver may have been running for a while.
PDF p06 l33: Impact:  These  issues  are  solver-blocking  whenever  a  user  tries  to  combine  text  permutations  with
PDF p06 l34: interruptors , or uses variable-count interruptors with any fixed permutation . The solve will
PDF p06 l35: either refuse to start (if checks catch it) or , worse, crash at runtime when a length mismatch arises mid-
PDF p06 l36: optimization. The interruptor pool range issue means a misconfigured pool (e.g., containing an index equal
PDF p06 l37: to ciphertext length) will not be caught until a specific key triggers an out-of-range removal, causing a late
PDF p06 l38: failure .

PDF p07 l18: api/normalize.py  & Tests – WLI Semantic Mismatch (Start/End vs Pos/Len)
PDF p07 l19: The Word Location Index (WLI)  is intended to carry word-position information for each character (rune) of
PDF p07 l20: the ciphertext. There is a fundamental ambiguity in how WLI is represented: - The API documentation and
PDF p07 l21: normalization code  treat WLI as a pair of  [start_index_in_text, word_length]  (effectively start
PDF p07 l22: offset and length of the word) for each character . For example, in a two-letter word, both letters would
PDF p07 l23: get WLI  [0, 2] according to  wli_from_text  and the docs. - The  scoring algorithms (language

PDF p11 l01: KeyOps and Cipher Fidelity Issues
PDF p11 l02: Overview:  KeyOps  are  responsible  for  generating,  mutating,  and  applying  keys  under  various  cipher
PDF p11 l03: definitions. For cryptanalytic fidelity, they must preserve invariant structures (e.g., permutation keys remain
PDF p11 l04: bijective, modular keys wrap correctly, etc.). Generally, RDP’s KeyOps implementations do follow expected
PDF p11 l05: patterns  (e.g.,  substitution  key  mutation  swaps  two  elements,  preserving  bijectivity).  The  problems
PDF p11 l06: identified lie in composite key handling and certain generic cipher implementations:
PDF p11 l07: generic_map_cipher.py  & core/runtime.py  – Collapsed Key Space for 
PDF p11 l08: user_map3  (Affine Cipher)
PDF p11 l09: The user_map3  cipher (an affine-like cipher with presumably two key components) is supposed to have a
PDF p11 l10: key domain of size A*A (if A is the alphabet size, there are two independent components, often denoted
PDF p11 l11: k1 and k2 for affine). RDP’s implementation, however ,  collapses this to an effectively one-dimensional
PDF p11 l12: space of size A  by applying modulo arithmetic prematurely:
PDF p11 l13: The cipher internally computes A_key = self.A * self.A  for the key space and expects a
PDF p11 l14: single integer key kv in 0..A*A-1 , which it then splits into k1 = kv // A, k2 = kv % A .
PDF p11 l15: But when decrypting, it immediately takes the provided key value mod self.A . This means
PDF p11 l16: only k2 (equivalent to kv % A) actually affects the output; k1 is effectively always zeroed out by the
PDF p11 l17: mod.
PDF p11 l18: Moreover , the KeyOps hints system and API both treat the key length as 1 (since 
PDF p11 l19: resolve_key_length  returns 1 for any tuple spec)  and use the cipher’s A as the modulo in
PDF p11 l20: mutation hints . The solver , thinking the space is size A, will only search 0..A-1.
PDF p11 l21: Evidence:  The code clearly shows  key_arr = key_arr % self.A  in the cipher’s decrypt routine ,
PDF p11 l22: meaning  any  key  beyond  A  wraps  around.  The  GenericMapCipher  constructor  sets  up
PDF p11 l23: A_key = self.A * self.A  if a second dimension is expected, but then doesn’t utilize it fully . In
PDF p11 l24: runtime.py  where key hints are gathered for KeyOps, it uses the cipher’s  A to inform the mutation
PDF p11 l25: space, not A*A. Also, the API’s resolve_key_length  simply returns 1 for tuple specs, preventing
PDF p11 l26: the solver from treating the key as having two independent parts .
PDF p11 l27: Impact:  This is solver-blocking  for any cipher meant to have two degrees of freedom like user_map3  (e.g.,
PDF p11 l28: Affine cipher  ax + b mod 29). The solver will be effectively stuck exploring only variations in  b (the
PDF p11 l29: second part), never changing a (the first part), because any attempt to change a is lost to the modulus.
PDF p11 l30: The cipher’s own tables might be built for a full A*A space (and indeed the encryption/decryption logic uses
PDF p11 l31: both k1 and k2), so if k1 != 0 is required for the correct key, the solver will not find it . Telemetry
PDF p11 l32: might not flag anything unusual; the solver just fails to find a solution.
PDF p11 l33: Recommendation:  Support  the  full  key  domain:  -  Option  1:  Represent  the  key  as  two  independent
PDF p11 l34: components (length 2 array) and adjust KeyOps accordingly (so that keyops.random  generates [k1, k2],
PDF p11 l35: mutate tweaks one or both, etc.). This way no mod reduction is needed; both parts are optimized. - Option
PDF p11 l36: 2: Keep encoding as single number 0..A A-1 but do not mod-reduce before decrypt*. Instead, compute k1
PDF p11 l37: and k2 from the full number so that k1 can be >0. The KeyOps hints should use  mod = A*A  for this
PDF p11 l38: cipher’s family so the solver explores the full range . - The API should not collapse tuple key lengths to 1•
