RDP Liber Primus Domain Spec v1 (Working)
Date: 2026-03-07 (America/Los_Angeles)
Status: Completed and implemented (LP0-LP5)
Location scope: src/rune_decrypter_prime/data/liber_primus

0) Purpose
- Define Liber Primus (LP) as a self-contained domain module with typed core APIs.
- Keep LP modelling separate from RDP solving.
- Define a thin, explicit adapter boundary from LP fragment retrieval to solver inputs.

1) Architectural boundary (non-negotiable)
- LP owns text modelling:
  - transcript parsing
  - page/line/word/glyph indexing
  - page schemes, partitions, routes, labels/features
- RDP owns solving:
  - scoring
  - search/optimization
  - campaign orchestration
- Adapter boundary:
  - LP -> RDP handoff uses solver-ready payloads (`ct_idx`, `wli`) plus optional metadata.

Design rule:
- No scattering LP types into core solver modules.
- LP domain modules may be extracted later without major solver refactor.

2) Current foundation (must be preserved)
Existing proven base remains canonical:
- `lp_transcript.py` with canonical glyph stream and span model.
  - Evidence: class `GlyphSpan`, `ct_wli`, `intersect`, split APIs.
- `lp_master.py` with master transcript load and canon page attachment (`0.jpg`..`57.jpg`).
- Existing LP API helpers in `api/data_helpers.py` remain functional during migration.

3) Domain model layers
3.1 Reference layer (naming)
- `LPBuiltInPageScheme` (explicit stable string values):
  - `transcript_page_id`
  - `bound_book_page`
  - `canon_unsolved_page`
- `LPPageRef` dataclass:
  - `scheme: LPBuiltInPageScheme`
  - `number: int`
- Optional custom typed labels:
  - `LPRegistryLabel(namespace: str, name: str)`

3.2 Fragment layer (selection)
- `LPFragmentLocator` dataclass:
  - `page_ref: LPPageRef`
  - optional `line`, `line_end`, `word`, `word_end`
  - negative indexing allowed for intra-container references
- `LPSectionOrdinal` dataclass:
  - canonical typed section key (e.g., `8`, `8-1`)

3.3 Partition layer
- `LPBuiltInPartitionScheme` (explicit stable string values):
  - `legacy_sections`
  - `red_rune_17`
  - `side_art_10`
  - `side_art_red_rune_nested`
  - `solved_plaintext_pages`
- `LPPartitionEntry`:
  - scheme
  - ordinal
  - canon page start/end
  - display/tags

3.4 Feature layer
- `LPPageFeature`:
  - solved/unsolved tags
  - side-art labels
  - aliases/display metadata

3.5 Route layer (post-retrieval only)
- `LPLineReadMode`:
  - `left_to_right`, `right_to_left`, `boustrophedon`
- `LPLineRuneSelector`:
  - `all`, `first_only`, `last_only`
- Shape routes:
  - `LPSpiralDirection`: `clockwise`, `counterclockwise`
  - `LPSpiralStartCorner`: `top_left`, `top_right`, `bottom_right`, `bottom_left`

4) Core invariants
- All custom registrations reduce to canon-based coordinates.
- Retrieval resolves first; route traversal applies second.
- Strict typed core APIs; no forgiving token parsing in core.
- Persisted semantics use explicit stable enum values (no `auto()` for persisted identity).

5) Indexing rules
- Transcript page ids: zero-based.
- Canon unsolved pages (`0.jpg`..`57.jpg`): zero-based.
- Bound-book pages: one-based.
- Bound-book mapping rule is explicit:
  - `bound_book_page = transcript_page_id + 1`
  - canonical unsolved pages map to the last 58 transcript pages only:
    - `canon_unsolved_page(0)` -> transcript page `total_pages - 58`
    - `canon_unsolved_page(57)` -> transcript page `total_pages - 1`
  - Therefore `bound_book_page(54)` and `canon_unsolved_page(54)` are different references.
- Line/word coordinates in resolved container: zero-based with negative indexing allowed.
- Negative page indices are not valid for built-in page schemes.
- Negative indexing is valid only inside already-resolved containers (lines/words within fragment/page).
- Out-of-range index behavior: `IndexError`.

6) Module split target
- `lp_transcript.py` (existing): parser + span/view mechanics.
- `lp_master.py` (existing): master loading + default canon catalogue.
- `lp_registry.py` (new): typed refs, schemes, partitions, registry model.
- `lp_locators.py` (new): locator normalization/resolution helpers (optional if merged into registry).
- `lp_partitions.py` (new): built-in partition constructors and validation.
- `lp_routes.py` (new): traversal helpers.
- `lp_features.py` (new): page feature/tag/alias model.
- `lp_ui_parse.py` (new): UI-only token parsing (`54.jpg`, `page 54`, etc.).
- `lp_adapter.py` (new): LP fragment -> solver payload bridge.

7) Public surface
Primary public imports should converge to one canonical LP surface under:
- `rune_decrypter_prime.data.liber_primus`
Compatibility:
- Existing helper APIs remain during transition, then deprecate duplicates in a controlled cycle.

8) Adapter contract (LP -> RDP)
Adapter output object:
- `ct_idx: list[int]`
- `wli: list[list[int]]`
- optional metadata:
  - page refs
  - partition/label identifiers
  - route used
  - fragment diagnostics (sizes, line count, etc.)

Rules:
- Adapter must be pure transformation; no solver logic.
- Adapter output must be deterministic for identical locator+route input.

9) UI parsing boundary
- `lp_ui_parse.py` handles human-friendly tokens.
- Core module APIs accept typed refs only.
- UI parser maps tokens into typed refs and locators.

10) Built-in catalogue v1
Required built-ins for first implementation:
- Page schemes:
  - transcript page id
  - bound-book page
  - canon unsolved page
- Partitions:
  - red-rune 17
  - side-art 10
  - nested side-art/red-rune
- `solved_plaintext_pages` is reserved and deferred beyond v1 core implementation.
- Features scaffold:
  - solved/unsolved tags
  - alias slots for solved-page labels

11) Route edge behavior contract
- Route composition:
  - line selectors (`all`, `first_only`, `last_only`) compose with all line read modes.
- Empty line behavior:
  - selector on empty line contributes no rune output.
- Ragged-grid spiral behavior:
  - fragment lines project to ragged grid with `None` gaps for short rows.
  - spiral traversal visits the bounding rectangle in route order.
  - `None` cells are skipped by default.
- Determinism:
  - same fragment + same route options must yield identical rune order.

12) Testing contract
Must-have tests before promoting LP typed API as preferred surface:
1. Resolver parity with existing canon mapping.
2. Fragment parity with existing `GlyphSpan` outputs (`ct_wli` equality).
3. Partition parity for built-in sections/ranges.
4. UI parser acceptance/rejection boundaries.
5. Backward compatibility tests for existing LP helper APIs.

13) Migration policy
- Incremental adapter-over-foundation migration only.
- No rewrite of existing `LPTranscript` internals in initial phases.
- Keep no-guessing, deterministic, and typed-core rules throughout.
