2 Spec v1.1 summary (verified from uploaded spec)
2.1 Goals and scope

The RDP Community Benchmark v1.1 aims to run a reproducible campaign where multiple contributors evaluate the solver on combined periodic substitution + columnar ciphers. Important goals include:

Self‑contained repo & CPU‑only: all assets are in‑repo and recombined by setup. Submissions must run on CPU; GPU scoring is out of scope.

Deterministic manifests, shards and results: no environment variables are allowed; stable hashing and canonical JSON serialisation must be used for fingerprints.

Compact outputs: results are JSONL and aggregated CSVs/heatmaps (no SQL or large artefacts).

The benchmark explores a matrix of period 7..13, columns 1..13, and both orders (col_then_sub, sub_then_col). A fixed profile catalogue defines solver tuning and permitted overrides (baseline and stage3‑fullband profiles). The campaign spec explicitly excludes solver algorithm changes and GPU/Torch scoring.

2.2 Determinism rules

The spec mandates stable determinism:

Use SHA‑256 over canonical JSON for all job IDs and fingerprints; never use Python’s built‑in hash().

Serialise JSON with sorted keys and no unnecessary whitespace (canonical form).

2.3 Manifest and result schemas

The manifest schema (manifest_schema_v1_1.json) lists required fields: campaign_id, job_id, git_sha, text_fixture_id, period, columns, order, profile_id, run_seed, replicate_idx and config_fingerprint. The result schema extends these with solver outputs: status, stop_reason, best_match_ratio, best_stage, total_seconds, total_evals, stage‑wise scores, and provenance fields device, scoring_backend, fastlm_present. Both schemas disallow additional properties.

2.4 Caps, status and stop reasons

Per‑job caps: each job’s campaign config must specify max_seconds_per_job and max_evals_per_job.

Status enum: solved, unsolved, stalled, error.

Stop‑reason enum: stable strings include: solved_threshold_met, time_cap_reached, eval_cap_reached, stage1_budget_exhausted, stage2_budget_exhausted, stage3_budget_exhausted, plateau_detected, no_candidates_to_promote, invalid_config, missing_assets, fastlm_unavailable, exception_raised. Precedence rules ensure consistent selection when multiple conditions apply.

No silent autoskip: campaign mode must never silently skip jobs (“proven autoskip”); resuming a previously completed job is the only allowed skip and must be logged.

2.5 Roles and workflows

The spec defines clear roles:

Setup and preflight: Recombine assets, build/verify _fastlm, run preflight checks to ensure imports and scoring functions work; write logs and benchmark_ready.json only on success. Preflight must confirm assets exist and match expected hashes, _fastlm works, and CPU scoring is functional. The process must be atomic, idempotent, and leave no partial artefacts.

Canary run: A short (6–12 jobs) smoke test covering both orders and a single profile; run after preflight to catch setup problems.

Runner: Each contributor runs an assigned shard using a simple local config (runner_id, shard path, output root, resume, optional max_jobs). The runner must operate in campaign mode with no autoskip, write results incrementally, and include logs in the run_bundle/ output.

Organiser: The coordinator validates each run_bundle (schema compliance, correct campaign id/sha, no duplicate job_id, CPU‑only fields); combines valid results deterministically (solved > unsolved, higher best_match_ratio, lower total_seconds, stable tie‑break); aggregates CSV summaries and heatmaps; and publishes a final outputs bundle.

3.2 Conflicts and determinism risks

Autoskip logic: existing local benchmark scripts might use “proven autoskip” or environment‑variable toggles; campaign mode forbids this and requires explicit resume logging. We must audit and guard against any autoskip behaviour.

Hashing functions: if any part of the code uses Python’s hash() for IDs or seeds, it must be replaced with SHA‑256 canonical JSON hashing. This needs code review in manifest generation and sharding.

Environment variables: the spec prohibits environment variables controlling benchmark behaviour. Any existing scripts reading env vars (e.g. for logging levels or autoskip) should be refactored into explicit config fields.

Parallelism & RNG: the solver may employ randomised heuristics or multi‑threading. Campaign seeds must be deterministic and reproducible. We need to ensure RNG seeding is tied to campaign seeds and that multi‑threading does not introduce nondeterminism (e.g. stable ordering of operations).

Asset recombination: recombining split assets must be atomic; partially written files could break determinism. A robust temporary directory and rename strategy is required.

Stability of string enums: statuses and stop reasons must match spec exactly; case‑sensitivity and typos in code could lead to invalid results that fail schema validation.

Scope and assumptions

The implementation targets the following behaviours described in the v1.1
specification:

Deterministic manifest generation based on a campaign seed and commit,
enumerating periods 7–13, columns 1–13 and both cipher orders
(col_then_sub and sub_then_col). The manifest includes a
deterministic job_id derived from the canonical JSON representation of the
job specification hashed with SHA‑256. The campaign_id is derived
similarly from the campaign seed. Canonical JSON uses sorted keys and
minimal separators to ensure stable ordering across platforms.

Sharding of the manifest into a configurable number of roughly equal‐sized
files with stable ordering. Shards are written to an output directory and
named manifest_shard_XXX.jsonl. The sharder does not drop or duplicate
jobs.

A prototype shard runner that reads a shard of jobs, loads a profile
catalogue, applies per‑job caps, and writes results rows conforming to the
v1.1 result schema. At this stage the runner contains a stub solver that
returns unsolved results with a missing_assets stop reason; the actual
solver integration will follow in later iterations. Logging and resume
support are present.

Organiser tooling comprising a validator (to check run bundles against
schemas and manifest contents), a combiner (to deduplicate and merge
multiple runs deterministically), and an aggregator (to produce CSV
summaries and simple heatmaps). These are implemented as separate scripts
to ease testing and future enhancements.

The following assumptions have been made due to limited visibility into the
full spec during this prototype:

The manifest schema requires only the fields exposed here
(job_id, campaign_id, campaign_seed, commit, period,
columns and order). Should additional fields be mandated (for
example a profile or replicate index) they can be added easily by
modifying the generate_jobs function in generate_manifest.py.

The result schema contains keys for basic meta data plus status,
stop_reason, best_match_ratio, total_seconds and
num_evaluations. It also mandates that status be one of
solved, unsolved, stalled or error, and that stop_reason
be one of the enumerated reasons defined in the spec. If additional fields
appear in the official schema they can be appended to the result row in
run_shard.py.

A simple deterministic tie‑break procedure is used in combine_results
consistent with the spec: when multiple result rows exist for a job, the
row with the lexicographically highest status, highest best_match_ratio
and lowest total_seconds is chosen. Should the spec require a
different priority order this function can be updated.
