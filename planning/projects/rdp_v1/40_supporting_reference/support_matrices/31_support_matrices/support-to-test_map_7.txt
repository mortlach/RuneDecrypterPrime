How to keep the workflow tightly controlled

This is the key part.

The handbook already gives you the right ideas: read-first order, no silent support reduction, no second config surface, no local output owner, no campaign-local scorer contract, parity before tidiness, and support-matrix cells protected by tests.

To make that real, I would enforce these seven hard rules:

1. No task without a task card

No code work starts unless the task card names:

contract affected

parity source

likely files

related tests

non-goals

acceptance checks

2. No task without the read-first order

Every contributor or agent must read:
CURRENT_PHASE → handbook → ADRs → ACTIVE_TODO → support matrix → relevant tests → relevant code.

3. No support reduction without explicit sign-off

If a change weakens a support promise, that is architectural and must be escalated. The handbook says this plainly.

4. No major tree churn before behaviour is protected

No broad campaigns/ relocation or rename-cleanup passes before:

mapping note is done

support meaning is frozen

guardrails exist

façade plan exists

5. Every slice must pass entry, review, and done gates

Not optional.
That is how you stop “small tidy refactors” from mutating architecture.

6. One live board, one live risk register, one findings register

Do not let chat be the tracker.
Use:

ACTIVE_TODO.md

CURRENT_RISKS.md

findings_register.csv

7. Stable truth must move upward

If something becomes stable, promote it out of private notes into:

charter

campaign spec

implementation plan

ADR

tests

Private notes support truth. They should not become the only truth. The handbook says exactly that.
