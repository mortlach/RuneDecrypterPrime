# RDP Phased Refactor Plan

## Uniform campaign runner surface, no-WLI first, contract-safe delivery

**Date:** 2026-03-02 (America/Los_Angeles)
**Last synced:** 2026-03-04 (America/Los_Angeles)
**Scope:** Strategy + campaign refactor in benchmark layer. No install/packaging work.

---

## 0) Summary

We will deliver the long-term target (“one runner surface, one stage/pool engine, staged adaptivity, span-hamming integrated”) as a **phased roadmap** with strict compatibility gates.

Key idea:

* **Prove the framework on no-WLI first** (harder problem; 500-char target on 5 real texts).
* Keep the **public v1.1 community benchmark contract unchanged** while we iterate internally.
* Introduce a **separate internal schema/version** for no-WLI and wider flavour/cipher space.
* Implement StageSpec/AdaptivePolicySpec first in the **tools/benchmarks layer**, not in the core engine.
* Treat “rich ScorerResult everywhere” as **phased**: sidecar telemetry first, runtime adoption later.

---

## 1) Contracts

### Track A — Public community benchmark v1.1 (unchanged)

**Hard contract:**

* Manifest/results JSONL row schemas remain unchanged.
* Public restrictions remain (CPU/NumPy compliance etc.).
* Dispatch remains limited to existing supported `order` values.
* No public enum widening (no overloading order for no-WLI).

**Allowed changes:**

* Internal implementation refactors that still produce identical v1.1 bundles.
* Additional *sidecar* artefacts (extra files) as long as:

  * they do not change v1.1 required rows
  * they don’t break validation

### Track B — Internal extended campaign (new schema/version)

**Purpose:**

* Express no-WLI flavour, periodic_sub, richer stage specs, span roles/budgets, and future WLI catalogue.

**Hard contract:**

* New schema/version with an explicit `flavour` (or equivalent).
* Internal dispatcher supports expanded flavour space.
* Promotion to Track A is gated and deliberate.

**Important rule:**

* Do not overload existing public enums; internal schema introduces explicit fields.

---

## 2) Architecture boundaries (near-term)

### “StageEngine” definition for this plan

In this wave, “StageEngine” means:

* a **benchmark-layer stage/pool engine** that orchestrates:

  * stages
  * candidate pools
  * pruning/diversity
  * telemetry
  * adaptive decisions

It is **not** a rewrite of `src/.../core/engine`.

### Where implementation lives

* StageSpec/AdaptivePolicySpec and shared orchestration live in:

  * `tools/benchmarks/periodic_sub_trans/common/...` (or equivalent)
* Existing flavour runners become thin wrappers around shared orchestration.

---

## 3) Guiding rules (non-negotiable)

1. **No forks**: no separate pipelines per cipher kind; cipher differences expressed as operator schedules in spec.
2. **Score-space correctness**: pool-collapsing decisions must use declared decision score spaces (no silent mixing).
3. **Span-hamming is budgeted**: every use has scope/cadence/budget, with cost accounting.
4. **Shadow mode first**: span evaluates and logs before it can influence decisions.
5. **Oracle separation**: benchmark-only oracle annotations allowed; production decision paths must be oracle-free.
6. **Determinism**: canonical JSON + SHA-256 fingerprints; seeded randomness only.

---

## 4) Preconditions (must be closed or explicitly guarded)

These are “gates” before we call the refactor implementation-ready.

### Gate P1 — scorer_schedule plumbing complete

If StageSpec depends on objective-catalog control, then the code must actually apply scorer schedules.

**Pass condition (all required):**

* One shared scorer schedule DTO exists and is the single internal representation of scoring schedule selection.
* All affected runners/adapters map `profile/config -> DTO -> effective scoring path` using the same DTO semantics.
* Tests prove that changing scorer_schedule changes the effective scoring path in:
  * community campaign adapter dispatch
  * periodic_sub_trans col_then_sub
  * periodic_sub_trans sub_then_col
  * periodic_sub_trans no_wli (internal scope is acceptable)
* Gate evidence includes test artefacts (not only logging statements).

### Gate P2 — no-WLI torch AVG/full_text stability

There is an open crash/stability gate.

**Pass condition (either):**

* (a) the crash is closed and reproducible stability is proven, or
* (b) a tested fallback/guard policy exists (and is logged) that keeps runs usable.

### Gate P3 — oracle / production decision separation

Benchmark flows may still compute oracle metrics.

Production decision paths are explicitly defined as:

1. stop score / stop condition evaluation
2. candidate prune/promote decisions (including tie-band expansion)
3. winner selection

Rule:

* When `oracle_mode=off` (production), oracle inputs MUST NOT be consulted by any production decision path.
* Oracle metrics may still be computed and logged as evaluation-only fields, but MUST NOT affect stop/prune/promote/winner decisions.

Required trace fields (oracle separation proof):

* `oracle_mode`: `off|benchmark_only`
* `oracle_consulted_in_decisions`: boolean

**Pass condition:** if `oracle_mode=off`, trace evidence shows `oracle_consulted_in_decisions=false` and code structure enforces the same rule for all production decision paths.

## 5) Phased plan

### Phase 0 — Contract safety and plumbing

**Goal:** make later work safe and meaningful.

**Deliverables**

* Track A: public v1.1 unchanged; validation still passes.
* Close P1 scorer_schedule plumbing *or* explicitly declare it out-of-scope with a replacement mechanism.
* Implement explicit oracle separation in runners/logging (benchmark-only vs production).
* Close P2 torch AVG/full_text stability gate or implement tested fallback/guard.

**Acceptance criteria**

* Public v1.1 run bundle generation and validation remain green.
* scorer_schedule is either functional and provably applied, or a documented alternative is adopted.
* no-WLI runs have a clear “torch stability” status: stable or guarded (never ambiguous).

---

### Phase 1 — Structural cleanup: make runners configurable and extract shared utilities

**Goal:** reduce coupling and enable shared stage orchestration.

**Deliverables**

* Replace mutable globals in each flavour runner with a typed “RunnerConfig” object.
* Extract shared non-algorithmic utilities into `periodic_sub_trans/common`:

  * deterministic ID/fingerprint helpers
  * snapshot writers for instances/stages/summary
  * consistent telemetry field naming
  * pool container type (candidate list + basin labels + dedupe helpers)

**Acceptance criteria**

* No change in baseline behaviour for col→sub and sub→col when using extracted utilities.
* Outputs remain comparable and validation continues to pass.
* No new CLI-driven tuning surfaces; workflows remain run-file driven.

---

### Phase 2 — StageSpec + AdaptivePolicySpec in benchmark layer (framework introduction)

**Goal:** introduce the stage/pool engine without rewriting solver internals.

**Deliverables**

* Define `StageSpec` and `AdaptivePolicySpec` (benchmark layer).
* Implement a StageEngine that:

  * runs a list of stages
  * maintains a pool
  * applies prune/diversity/tie-band rules
  * records stage telemetry and decision trace
* Port **col→sub** and **sub→col** runners to use StageEngine orchestration while preserving their current search shapes.

**Acceptance criteria**

* For col→sub and sub→col:

  * StageEngine-driven runs match baseline outcomes within agreed tolerances.
  * Stage-level telemetry exists and is consistent.
* StageEngine is demonstrably “one engine” across those two flavours (spec changes only).

---

### Phase 3 — no-WLI integration into the same framework (no-WLI first-class)

**Goal:** use the framework on the harder no-WLI problem.

**Deliverables**

* Add no-WLI flavour as a StageEngine-usable configuration:

  * either as a third wrapper runner that calls StageEngine, or
  * as an internal dispatch flavour in Track B (if ready)
  * add an internal-only `configure_campaign_run(...)` entrypoint in no_wli runner, aligned with other flavours; it may enforce one canonical order with explicit config errors for unsupported orders
* Make the “no-WLI 500-char target” the primary acceptance metric:

  * 5 real texts, tracked solve rate vs time/cost.
* Keep all solver inner loops numeric (no invasive scoring API changes yet).

**Acceptance criteria**

Phase 3 Acceptance (revised; order capability aligned)

* Required in Phase 3:
  * One canonical no-WLI order path is runnable under StageSpec/PolicySpec with uniform stage telemetry and trace outputs.
  * The previously proven p7 ~1000-char path is representable as a concrete StageSpec list under that canonical order.
  * no-WLI span-hamming shadow mode can run on that canonical order and produces cost + counterfactual telemetry.
* Not required in Phase 3:
  * Supporting both no-WLI orders (`col_then_sub` and `sub_then_col`) under unified dispatch.
* Deferred to Phase 5 (Track B dispatch):
  * Both no-WLI orders supported under a unified internal dispatcher/schema.

---

### Phase 4 — Span-hamming standardisation: shadow mode → decision roles

**Goal:** incorporate span-hamming “fully”, safely, and measurably.

**Deliverables**

* Span roles become first-class in StageSpec:

  * off/shadow/prune/gate/combined/judge
* Shadow mode instrumentation includes:

  * deterministic selection of evaluated candidates
  * cost accounting (calls/time percentiles)
  * prune-point counterfactuals (“what span would have done”)
* Add “budgeted span evaluation” primitives:

  * scope (basin reps preferred)
  * cadence (every N / plateau / ambiguity)
  * two-pass lite→full option
* After shadow success, enable at least one decision-role pathway in no-WLI:

  * Stage B span-prune and/or Stage C gated span usage.

**Acceptance criteria**

* Shadow mode success checklist is met:

  * deterministic
  * provenance unambiguous
  * cost accounting consistent
  * counterfactual prune-point fields present
* Turning span from shadow→prune changes decisions only when enabled in spec.
* Span cost is visible per stage; runs can be tuned rationally.

---

### Phase 5 — Track B internal extended campaign schema + dispatch

**Goal:** unify expanded flavour space without touching public v1.1.

**Deliverables**

* Introduce `internal_campaign_schema_vNext` with explicit:

  * `flavour` (no_wli vs wli)
  * `cipher_family` (including periodic_sub)
  * richer StageSpec catalog references
* Add internal dispatcher that can run:

  * no-WLI periodic_sub / col→sub / sub→col
  * WLI catalogue later (defined, not necessarily implemented first)
* Ensure internal results can still be collated and audited similarly to v1.1.

**Acceptance criteria**

* Track B runs are reproducible and collatable with stable IDs and outputs.
* No changes required to Track A v1.1 validation pipeline.
* Internal schema can represent the “500-char no-WLI push” and sweep curated option sets.
* Both no-WLI orders (`col_then_sub` and `sub_then_col`) are supported under a unified internal dispatcher/schema.

---

### Phase 6 — ScorerResult evolution (sidecar → optional API → pervasive)

**Goal:** move towards richer scoring outputs without breaking solver loops.

**Deliverables**

* Phase 6.1: structured scorer sidecar outputs (ScoreBundle/ScorerResult) for:

  * survivors/top-k per stage
  * basin representatives
  * final winners
* Phase 6.2: optional API exposure (opt-in) for new components
* Phase 6.3: pervasive runtime adoption only after compatibility wrappers exist and performance impact is understood

**Acceptance criteria**

* Existing tutorial/solver flows remain functional without modification.
* Sidecar outputs are stable and enable deeper offline analysis.
* Any runtime adoption is gated by performance and compatibility tests.

---

## 6) Global acceptance criteria (what “success” means overall)

### Minimum success (end of Phase 4)

* One StageEngine orchestrates at least col→sub and sub→col in benchmark layer.
* no-WLI is first-class under StageSpec/AdaptivePolicySpec.
* Span-hamming is integrated with shadow mode and cost accounting, and can be promoted to decision roles safely.
* Public v1.1 remains unchanged and valid.

### Target success (end of Phase 5)

* Internal Track B campaign can dispatch expanded flavour/cipher space (including periodic_sub).
* The no-WLI 500-char target on 5 real texts is the main benchmark loop producing tuning evidence.
* Community benchmark sweeps can sample curated strategy/scoring options with comparable telemetry.

---

## 7) Explicit risks and mitigations

1. **More trials → more wrong-but-good basins**
   Mitigation: basin-aware pruning, tie-band rules, independent judge signals (span) and cost-aware adaptivity.

2. **Span-hamming cost dominates runtime**
   Mitigation: strict budgets, basin-rep scope, cadence, two-pass lite→full, shadow-first evidence.

3. **Score-space confusion undermines decisions**
   Mitigation: explicit objective identity (normalisation + window policy), decision score space declared, provenance logged.

4. **Refactor breaks public v1.1**
   Mitigation: two-track contract; Track A unchanged; Track B for expansion.

---

## 8) What we are deliberately leaving open (by design)

* Span-hamming’s role in WLI mode (allowed option, off by default).
* The “canonical” adaptive scaling rule (to be discovered; use curated policy menu).
* The “best” span integration pattern (judge/prune/gate/combined), explored via benchmark sampling after shadow.

---

# Phase 2 checklist

## StageSpec + AdaptivePolicySpec in benchmark layer

### P2.1 Define the spec types (benchmark layer)

**Goal:** introduce StageSpec/AdaptivePolicySpec as typed objects that can be instantiated from config without touching core engine.

* [ ] Create `tools/benchmarks/periodic_sub_trans/common/stage_spec.py`

  * `StageSpec`
  * `AuxObjectiveBinding`
  * `StageBudget`
  * `PrunePolicy`
  * `DiversityPolicy`
  * `PlateauPolicy`
  * `TelemetryRequirements`
* [ ] Create `tools/benchmarks/periodic_sub_trans/common/policy_spec.py`

  * `AdaptivePolicySpec`
  * `ScalingPolicySpec` (menu-based; IDs only for now)
* [ ] Create `tools/benchmarks/periodic_sub_trans/common/catalogs.py`

  * `ObjectiveCatalog` (IDs → scorer factory + identity/provenance)
  * `OperatorCatalog` (IDs → operator functions / move schedules)
* [ ] Ensure these specs can be created from existing runner/profile config patterns without adding new CLI knobs.

**Acceptance checks**

* [ ] Specs can be instantiated deterministically from a dict and round-tripped to canonical JSON for hashing.
* [ ] Unsupported operators/objectives cause a config error early (no silent no-ops).

---

### P2.2 Implement StageEngine skeleton (benchmark layer)

**Goal:** orchestrate “stage loop + pool + pruning + telemetry” while preserving existing flavour behaviour.

* [ ] Create `tools/benchmarks/periodic_sub_trans/common/stage_engine.py`

  * `StageEngine.run(spec, problem, seed) -> RunArtifacts`
  * stage execution loop:

    * initialise pool from seeds
    * run stage search loop (delegated to existing flavour-specific search functions)
    * apply prune/diversity/tie-band rules
    * emit stage summary + decision trace
* [ ] Create `tools/benchmarks/periodic_sub_trans/common/pool.py`

  * `Candidate` (candidate_id, basin_id, score_bundle pointer/summary)
  * `CandidatePool` (list + basin index + dedupe)
  * helpers:

    * `dedupe_before_prune`
    * `cap_per_basin`
    * tie-band expansion

**Acceptance checks**

* [ ] StageEngine can run with “Stage A only” and produce stage telemetry.
* [ ] Pool pruning produces deterministic results given the same seed/spec.

---

### P2.3 Port col_then_sub and sub_then_col to StageEngine orchestration

**Goal:** keep solver logic stable but move orchestration into shared code.

* [ ] In `tools/benchmarks/periodic_sub_trans/col_then_sub/runner.py`

  * wrap existing stage loops into functions callable by StageEngine, e.g.:

    * `run_discovery_stage(...)`
    * `run_promotion_stage(...)`
    * `run_refinement_stage(...)`
  * replace the existing “main orchestration” with:

    * build StageSpec list (or map existing profile into StageSpecs)
    * call StageEngine
* [ ] Repeat for `tools/benchmarks/periodic_sub_trans/sub_then_col/runner.py`
* [ ] Keep existing output artefacts (instances/stages/summary) identical where possible.

**Acceptance checks**

* [ ] For a fixed seed and a known small test case, outputs match baseline within tolerances.
* [ ] Existing unit tests and benchmark smoke tests still pass.

---

### P2.4 Telemetry wiring (minimal but uniform)

**Goal:** produce a uniform stage-row + trace stream without changing public v1.1 result rows.

* [ ] Add `trace.jsonl` writer in `periodic_sub_trans/common/io.py` (or similar)

  * `stage_start`, `stage_end`, `policy_decision`, `prune_applied`, `error`
* [ ] Ensure stage rows include:

  * pool in/out
  * basin_count, dup_rate, domination_ratio
  * score stats (best/median/spread/margin)
  * budget used
  * stage wall time
* [ ] Make filenames include unique run/job identifiers (avoid second-resolution timestamp collisions).

**Acceptance checks**

* [ ] Trace is readable without code context (stage_id, rule_id, what changed).
* [ ] No changes required to public v1.1 `results.jsonl` row schema.

## no-WLI first-class under StageSpec/PolicySpec

### P3.1 Introduce a no-WLI flavour wrapper that calls StageEngine

**Goal:** no-WLI uses the same orchestration framework, even if dispatch remains internal.

* [ ] Create/modify `tools/benchmarks/periodic_sub_trans/no_wli/runner.py`

  * expose stage functions compatible with StageEngine (same shape as col/sub runners)
  * replace internal orchestration with StageEngine (as far as realistic)

**Acceptance checks**

### P3.2 Basin identity and diversity rules become explicit and shared

**Goal:** stop “more seeds = worse” via deterministic diversity controls.

* [ ] Define basin/dedupe keys in one place (common module)

  * initial default: `end_hash` basin key
* [ ] Ensure dedupe happens before K and max-per-basin enforcement is applied consistently.

**Acceptance checks**

* [ ] Doubling seeds increases basin_count but does not explode duplicates retained.
* [ ] Pruning decisions are stable and auditable.

---

### P3.3 Oracle separation enforcement

**Goal:** benchmark-only oracle use is clearly separated from production decisions.

* [ ] Add an explicit flag in spec/config:

  * `oracle_mode: off|benchmark_only`
* [ ] Define production decision paths explicitly in spec/code:

  * stop score / stop condition evaluation
  * candidate prune/promote decisions (including tie-band expansion)
  * winner selection
* [ ] Ensure any oracle metrics are written as:

  * evaluation fields only
  * not referenced by production decision code paths (enforced by code structure)
* [ ] Emit required trace fields for proof:

  * `oracle_mode`
  * `oracle_consulted_in_decisions`

**Acceptance checks**

* [ ] If `oracle_mode=off`, trace proves `oracle_consulted_in_decisions=false`.
* [ ] Production mode decisions (stop/prune/promote/winner) are oracle-free by code structure and tests.
* [ ] Benchmark-only mode may log oracle evaluation fields, but they do not influence production decisions.

# Phase 4 checklist

## Span-hamming: shadow mode → decision roles (budgeted, measurable)

### P4.1 Span roles become first-class in StageSpec

**Goal:** make span integration explicit and enforceable.

* [ ] Extend `AuxObjectiveBinding` to include:

  * `role`: off/shadow/prune/gate/combined/judge
  * `eval_scope`: basin_reps/top_k_global/all
  * `cadence`: once_end/every_n_rounds/on_plateau/on_ambiguity
  * `budget_ms` / `budget_calls`
  * `span_profile`: lite/full
  * optional two-pass policy (lite→full)

**Acceptance checks**

* [ ] StageEngine enforces: role=shadow cannot affect pruning/winner selection.
* [ ] Missing budgets for span when enabled cause config error (or explicit fallback).

---

### P4.2 Standardise span cost telemetry (stage + instance)

**Goal:** cost accounting is consistent and sums correctly.

* [ ] Ensure span scorer evaluation returns cost info (or is timed centrally):

  * wall_ms per call
  * calls total
  * active/rejected/gated counts (when relevant)
* [ ] Add required counters to:

  * stage rows
  * instance summary
  * diagnostics.json

**Acceptance checks**

* [ ] `span_seconds_total` equals sum(per-event wall_ms) within tolerance.
* [ ] `span_active_rate` is always numeric (no NaN), even when span disabled/shadowed.

---

### P4.3 Shadow counterfactuals at prune points

**Goal:** “what span would have done” is visible without manual diffing.

* [ ] In StageEngine prune step, when span role=shadow:

  * compute span ranking for the evaluated subset
  * log:

    * shadow_span_winner_id
    * shadow_span_changed_winner
    * shadow_span_rank_of_actual_winner
    * overlap metrics (keep/drop sets, bounded lists)
* [ ] Write these to:

  * trace.jsonl as `span_shadow_counterfactual` event
  * stage summary row (minimal fields)

**Acceptance checks**

* [ ] Reviewers can read trace and understand whether span would have changed promotion.
* [ ] Counterfactual fields are present only when applicable and are bounded in size.

---

### P4.4 Budgeted evaluation scope (basin reps first)

**Goal:** span is “fully incorporated” without runaway cost.

* [ ] Implement evaluation selection policies:

  * default: 1–2 reps per basin
  * tie-band expansion for ambiguous cases (bounded)
* [ ] Implement budget clamp:

  * convert budget_ms into calls_affordable using measured p90 call time
  * stop evaluating once budget hit
* [ ] Implement two-pass:

  * lite on broad set
  * full on top-M or tie band

**Acceptance checks**

* [ ] Increasing seeds increases span calls roughly with basin_count until budget clamps.
* [ ] Span never evaluates unboundedly; budget-hit is logged explicitly.

---

### P4.5 Promote span from shadow to decision role (after shadow success)

**Goal:** span actually affects outcomes only after proven safe.

* [ ] Define “shadow success” checklist in code/tests:

  * determinism
  * provenance present
  * cost accounting consistent
  * counterfactuals emitted
* [ ] Enable at least one decision-role pathway in no-WLI:

  * Stage B span-prune (basin selection), or
  * Stage C gated span usage
* [ ] Add a small A/B benchmark harness:

  * same seeds/spec with span=shadow vs span=prune
  * report: decision changes + cost delta + solve outcome delta (benchmark-only)

**Acceptance checks**

* [ ] Turning span decision role on/off changes behaviour only through spec, not code forks.
* [ ] Cost/benefit is measurable per stage and per run.
