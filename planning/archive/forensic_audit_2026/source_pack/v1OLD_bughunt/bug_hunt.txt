Score ordering invariant: same plaintext set scored by numpy vs torch backend yields identical ordering (not necessarily identical floats).

Dtype boundary trap: float64 baseline tables vs float32 runtime produces no rank inversions on a fixed adversarial plaintext set (especially near ECDF clamp edges).

Windowing boundary correctness: minimal plaintext lengths around the window size produce stable, monotone behaviour (no “sawtooth” scoring jumps).

Cache key correctness: same plaintext on same device → same score across runs; different plaintext with same length → different cache key (no collisions).

Determinism across devices: CPU and CUDA runs with fixed seed produce identical chosen best plaintext after fixed number of evals (even if intermediate paths differ).

Telemetry truth test: “since last improvement” increments only when best score is unchanged; never resets on equal-score ties unless explicitly intended.

def _should_include(path: str) -> bool:
    if WHITELIST_PATHS:
        return path in WHITELIST_PATHS
    return any(path.startswith(pref) for pref in INCLUDE_PREFIXES)


def _pin_raw_url(raw_url: str) -> str:
    # repo_links.json appears to use raw URLs like:
    # https://raw.githubusercontent.com/mortlach/RuneDecrypterPrime/dev/<path>
    needle = "/RuneDecrypterPrime/dev/"
    if needle in raw_url:
        return raw_url.replace(needle, f"/RuneDecrypterPrime/{COMMIT_SHA}/")
    return raw_url


def _download_text(url: str) -> bytes:
    req = Request(url, headers={"User-Agent": USER_AGENT})
    with urlopen(req, timeout=TIMEOUT_S) as resp:
        return resp.read()


def _safe_mkdir(p: Path) -> None:
    p.mkdir(parents=True, exist_ok=True)


def _write_bytes(path: Path, data: bytes) -> None:
    _safe_mkdir(path.parent)
    path.write_bytes(data)


def _zip_dir(src_dir: Path, zip_path: Path) -> None:
    if zip_path.exists():
        zip_path.unlink()
    with zipfile.ZipFile(zip_path, "w", compression=zipfile.ZIP_DEFLATED) as zf:
        for file_path in src_dir.rglob("*"):
            if file_path.is_file():
                arcname = file_path.relative_to(src_dir)
                zf.write(file_path, arcname.as_posix())

        raise FileNotFoundError(f"Cannot find repo_links.json at: {REPO_LINKS_JSON}")

    print(f"Skipped:  {skipped}")
    print(f"Failed:   {failed}")
    print(f"Folder:   {OUT_DIR}")
    print(f"Zip:      {OUT_ZIP}")

You’re right that we do need “absolute indices from the start of the text” in RDP — but that’s not WLI. That absolute-index structure already exists and is the interruptor positions machinery.

What’s going wrong in the repo is that a different feature (word/word-break metadata) got muddled with “absolute start offsets”, and then a helper tried to “convert” it, making the confusion worse.

Below is the evidence-bound cross-check from your zip.

1) Absolute indices for interruptors are real, intentional, and separate

Interruptors are configured as absolute indices into the ciphertext. That is exactly what you described (“so we know how to remove/add interruptors while solving”).

Evidence

core/config/interruptor.py :: InterruptorConfig

comment + fields explicitly say positions and absolute indices:

exact: Optional[List[int]] and pool: Optional[List[int]] are described as “exact positions (absolute indices)”

index_space: str = "absolute" # "absolute" only for now

So: yes, there is a canonical “absolute index list” concept — it’s interruptors, not WLI.

2) WLI is supposed to mean “position-in-word + word-length” in scoring

Your statement “for scoring it’s index in word and length of the word” matches what the scorers actually consume.

Evidence

scoring/hamming/backend.py

Word splitting uses pos == 0 to detect a new word:

pos = int(w[0]); if pos == 0 and cur_r: ...

That only makes sense if w[0] is position in word, not absolute start offset.

api/normalize.py :: runes_from_indices

It groups words using:

if wli[i][0] == wli[i][1] - 1: ...

That only makes sense if wli[i] == (pos_in_word, word_len) because “end of word” is when pos == len-1.

So the scoring + rendering paths are clearly written for pos/len WLI.

3) The “second WLI structure” (start/end or start/len) is not a valid alternative WLI for scoring

Here’s the crux: the API/config layer documents and coerces WLI as if it were “start/end spans” (or “start,length”), but the scorers treat it as pos/len.

3.1 The string-derived WLI builder currently emits “absolute start offset + word length”

Evidence

api/normalize.py :: wli_from_text

It accumulates pos across words and writes [pos, ln] for each rune in the word, then increments pos += ln.

That means the second word’s runes get e.g. [start_offset_of_word_in_text, word_len] — absolute indexing, not pos-in-word.

So that builder is not producing what scoring expects.

3.2 The config layer explicitly validates WLI as “(start, end)”

Evidence

core/config/cipher.py :: CipherConfig.__post_init__

It says: wli_data items must be (start, end) pairs per docs

And validates start <= end.

That is a different concept again (span end, not word length).

3.3 A helper converts the string WLI into “(start,end)” spans using a heuristic

Evidence

api/pipeline_helpers.py :: coerce_wli_for_config

It sets needs_span_conversion = any(pair[1] < pair[0] ...)

Then if conversion triggers: end = start + (span - 1)

This is the “why it explodes on multi-word input” mechanism:

First word: start=0, len maybe 2 → pair[1] < pair[0] false

Second word: start maybe 2 or 3, len maybe 2 → now 2 < 3 true → conversion triggers for all pairs → the meaning silently changes again.

4) Why this mistake likely happened (and why it’s dangerous)
Why it happened (very likely)

There are two genuine needs in the project:

Interruptor positions: absolute indices into the ciphertext (needed for remove/add logic).

Word-break features: per-rune metadata for scoring (needs pos-in-word, because the scorer uses pos==0 and packs into small fixed-width fields).

The bug came from re-using the same “WLI-ish pair of ints” shape for both, and then trying to “normalise” it at the API boundary without a strict invariant.

You can see the confusion right inside api/normalize.py:

make_single_word_wli docstring claims “WLI is always [start,length]” but the implementation returns [[i, L] for i in range(L)] — which is actually pos/len.

Then wli_from_text explicitly implements the docstring version (start offset + len).
So even within one file, the “truth” diverged.

Consequences (real, solver-impacting)

If WLI-based scoring is enabled, multi-word string inputs will produce WLI that:

is not pos/len,

may be converted into spans,

and then gets interpreted by scorers as pos/len anyway.

That can:

break word segmentation (pos==0 logic),

distort WLI features,

and for hard solves, flatten or randomise the optimisation signal in the WLI component.

Separately: interruptor absolute indices are fine — but this WLI confusion makes it easy for a developer to think “WLI means absolute offsets” and accidentally route the wrong structure into scoring.

5) The key design takeaway

You were essentially asking:

“Is the alternative WLI structure completely wrong, or is it used for something else?”

Answer:

The absolute-index structure is legitimate — but it is InterruptorConfig.exact/pool, not WLI.

The “WLI as (start,end)” contract is not a legitimate alternate WLI for scoring in the current code. It’s a mismatched, misleading API/config contract that clashes with the scorer’s actual contract.

6) What I recommend you do next (no shims, strict)

To keep both concepts (which you do need):

Keep interruptors as absolute indices (as now). Don’t touch that meaning.

Make WLI unambiguously pos_in_word + word_len everywhere that touches scoring.

Remove/forbid the “(start,end)” WLI interpretation in CipherConfig or rename it to something else entirely (e.g. word_spans) if you truly want spans later.

And add one killer test that will prevent the confusion returning:

Test: multi-word string input path must yield WLI pairs satisfying 0 <= pos < len, and must have multiple pos==0 entries (one per word).

That will fail today, and it directly guards against mixing “absolute index” with “pos in word”.

Subsystem: CompositeKeyOps interruptor mutation locality (repair steps can amplify a “small” move)

A. Observed behaviour

drops negatives (sentinel),

Optimisers can behave like they’re making local moves but actually jump around in the interruptor set representation → solver-degrading and can become solver-blocking on hard, mixed ciphers (interruptor positions are extremely high-impact).

Subsystem: Periodic substitution key validity is assumed (not enforced) — encryption can silently go wrong

A. Observed behaviour
Periodic substitution decrypt is a direct gather using the provided key blocks. Encryption inverts each block by using the key values as indices into an inverse table.

There is no explicit validation that each phase block is a bijection over [0..A-1].

For every phase r, keys[r*A:(r+1)*A] must be a true permutation of 0..A-1.

Subsystem: Columnar transposition core logic looks internally consistent for edge lengths (but batch semantics are “broadcast plaintext”)

Chunk 7B — Cipher correctness: round-trip invariants and edge lengths
Subsystem: Cipher pipeline composition (interruptors + text transposition/permutation + core cipher)

A. Observed behaviour
CipherPipelineMixin.decrypt() and .encrypt() do:

remove interruptors (absolute indices),

apply text transposition / explicit permutation to the core text,

apply key transposition,

run _core_*_batch,

undo text transposition/permutation, then reinsert interruptors.

So plaintext returned by decrypt() is back in canonical order, and interruptors are restored to the original length.

B. Implicit contract

Interruptor indices are absolute positions in the original text (pre-removal).

initial_text_permutation_indices (if used) is a true permutation of indices 0..L_core-1, where L_core = L_full - (#interruptors removed).

C. Risk if violated

If the permutation is not actually a permutation (duplicates / missing indices), the “undo” step can become non-invertible or non-deterministic, producing plausible-looking but wrong plaintext that will not converge.

D. Evidence in code

Pipeline stages are explicitly spelled out in rune_decrypter_prime/ciphers/ciphers_pipeline.py :: CipherPipelineMixin.decrypt() and .encrypt():
