Dev note — PhaseB Runeberg NOSE damage ladder prototype
Purpose

Please wire in and smoke-test:

tools/benchmarks/periodic_sub_trans/no_wli/analysis/run_phaseB_runeberg_nose_damage_ladder_v1.py

This is a report-only Phase B benchmark. It must not change scorer weights, production scorer defaults, or dictionary policy.

The aim is to test whether PhaseA14 span-Hamming evidence survives across many Runeberg book chunks, controlled damage models, and null models. We are deliberately not optimising around the previous len6 HD<=2 result. The v0.3 plan says Phase B should generate the full strict/normal length/HD ladder, run positive/bad/null corpora, report observed/null/excess/lift, and only then decide useful/noisy rungs.

Important contract

Use:

NOSE only
both fwd and rev
500 rune-token chunks
PhaseA14 strict + normal selected dictionaries
full v0.3 enabled HD ladder
fast raw fingerprint counts
report-only outputs

Do not use:

WISE
LMPrime score files
old dictionaries
production scorer changes
the accidentally uploaded npz examples

The existing parser saves tokenised book files as tokenized/<book>_<dir>.npz, and stores the required NOSE arrays as pt_nose_data and wli_nose_data. The parser loader also expects the same keys when reusing tokenised files.

Expected local inputs

The script currently expects these relative paths from the repo root:

lmprime_out/tokenized/
assets/hamming_dictionary_policies_phaseA_v0_14/

Each selected book must have both files:

<book>_fwd.npz
<book>_rev.npz

If only one direction exists, the script should skip that book. That is intentional.

Leave this at the top:

RUN_MODE = "smoke"

Do not start with pilot or full.

Smoke mode should be tiny:

Things to watch

The script currently uses FINGERPRINT_MAX_CANDIDATES_PER_WINDOW = 0, intended as uncapped fingerprint mode. Cross-check that the backend really interprets 0 as uncapped in the current source.

The script uses max_hd=2 in SpanHammingConfig only because the constructor requires it; fingerprint mode should bin HD independently. Cross-check this against the backend implementation.

The rolling summaries are descriptive. They are useful for smoke/pilot timing and sanity checks, but they are not yet the final damaged-vs-null decision table.

Success criteria for smoke

Smoke is successful only if:

1. no crash
2. fwd and rev both appear
3. strict and normal both appear
4. clean, damaged, and null samples all appear
5. full ladder rows appear
6. timing checkpoints are written
7. final summary is written
8. candidate cap pruning is zero
9. rerunning with same config is deterministic
10. no production scorer files change

After that, the next step is a pilot run, not a scorer change.
